# SentinelVision AI

**Integrated CCTV Management & AI Video Analytics Platform** — Gujarat Police Innovation Hackathon 2026 proof of concept.

SentinelVision AI unifies heterogeneous CCTV sources behind one command-center interface: camera registration with secure credentials, live browser monitoring, AI vehicle/person detection (YOLO), automatic number-plate recognition (PaddleOCR), per-camera tracking, plate-confirmed cross-camera vehicle search and tracking, a GIS map (Leaflet/OpenStreetMap), alerting with WebSocket push, event history, CSV reports, and role-based access control (admin / operator / viewer).

> **Demonstration honesty:** this is a hackathon-scale proof of concept. Synthetic demo data is generated by the seeder and **visibly labeled `DEMO`** everywhere it appears. No real government CCTV credentials are used, no fake live feeds are shown, OCR output below the confidence threshold is flagged for human review, and no untested scalability claims are made (see `docs/SCALABILITY.md`).

## Architecture at a glance

```
┌────────────┐   HTTP/WS (same-origin proxy)   ┌──────────────────────┐
│  React SPA │ ──────────────────────────────► │  FastAPI (API only)  │
│ (Vite/TS,  │                                  │  auth · CRUD · GIS   │
│  Tailwind, │ ◄────────────────────────────── │  reports · WebSocket │
│  Leaflet)  │   MJPEG frames + live events    └──────────┬───────────┘
└────────────┘                                            │ SQLAlchemy
                                                          ▼
             ┌────────────────────────────┐        ┌──────────────┐
             │ Ingestion worker (separate)│───────► │ PostgreSQL / │
             │ RTSP · files · webcam      │  shared │   SQLite     │
             │ YOLO → tracker → ANPR      │  disk   └──────────────┘
             │ → events → alerts          │  (live frames)
             └────────────────────────────┘
```

- **API process never decodes video or runs inference.** The ingestion worker owns all capture/AI loops and publishes annotated frames to a disk-backed live store; the API streams them to browsers (MJPEG) and persists detection events.
- **Graceful degradation:** without the optional AI stack the platform still runs (management, streaming where sources allow, search, alerts, reports) and clearly reports `DEGRADED` AI status in the UI.

See `docs/ARCHITECTURE.md` for details and `docs/SCALABILITY.md` for the path toward large fleets (with explicit assumptions; no fabricated benchmarks).

## Quick start (Windows, no Docker)

Prerequisites: **Python 3.11+**, **Node 18+**. FFmpeg is optional (OpenCV bundles what it needs for most RTSP/File sources).

```bat
:: ---- Backend ----
cd backend
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
copy ..\.env.example .env          :: optional; defaults work for dev

python -m app.seed                 :: demo users + clearly-labeled synthetic data
python make_demo_video.py ..\data\demo_videos\demo_traffic.mp4 20

:: terminal 1
python -m uvicorn app.main:app --port 8000
:: terminal 2
python -m app.workers.ingestion
```

```bat
:: ---- Frontend (new terminal) ----
cd frontend
npm install
npm run dev                        :: http://localhost:5173
```

Open **http://localhost:5173** and sign in:

| Account | Password | Role |
|---|---|---|
| `admin` | `Admin@12345` | full control |
| `operator` | `Operator@12345` | monitoring, search, alert acknowledgment |
| `viewer` | `Viewer@12345` | read-only |

> **Change or remove these accounts before any real deployment.** They exist for the demo only.

### See live video in 60 seconds

1. Log in as `admin` → **Camera Management** → edit `DEMO-SG-001` (or register a new camera).
2. Point it at any source you are authorized to use:
   - the generated clip: `data/demo_videos/demo_traffic.mp4` (protocol *file*),
   - a local webcam (protocol *webcam*),
   - your own RTSP URL (protocol *rtsp*, credentials entered in the credential fields — never embedded in the URL).
3. The worker picks it up within ~5 s; the tile turns **online** and starts streaming. With the AI stack installed, detections appear on the video and in the analytics pages.

### Enabling the AI stack (optional)

```bat
pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu   :: CPU build
pip install ultralytics                                                          :: YOLOv8
pip install paddlepaddle paddleocr                                               :: ANPR OCR
```

Restart the ingestion worker. The **AI Analytics** page shows `READY` for each component (and the GPU device when `ENABLE_GPU=true` with a CUDA torch build). First run downloads YOLOv8n weights automatically.

### Extended AI modules (optional, all independent)

Five additional modules ship alongside the core pipeline. Each has its own service file, its own `ENABLE_*` flag, its own lazy singleton and its own failure isolation — a broken module can never affect vehicle detection, ANPR, tracking or the live stream:

| Module | Flag | What it does | Works without heavy deps? |
|---|---|---|---|
| Vehicle Attribute Recognition | `ENABLE_ATTRIBUTES` | Color (HSV histogram) + body-style refinement per detection; stored in a separate table | Yes (heuristic tier) |
| Vehicle Re-ID | `ENABLE_REID` | Appearance fingerprints; cross-camera candidate matches recorded as **unconfirmed** (appearance ≠ identity) | Yes (heuristic tier; optional torch embedding) |
| Person Detection | `ENABLE_PERSON_MODEL` | Its own model instance, separate from the vehicle YOLO pipeline; presence-only rows | Needs `ultralytics` |
| Image Quality Assessment | `ENABLE_QUALITY` | Blur/brightness/visibility scoring of sampled frames; purely informational | Yes (pure OpenCV) |
| Anomaly Detection | `ENABLE_ANOMALY` | Speed / loitering / direction heuristics → **review events only**, never criminal labels | Yes (heuristics) |

Query them via `/api/v1/ai-modules/*` (status, attributes, reid-matches, quality, persons, anomalies). Status appears on the existing **AI Analytics** page; attributes enrich the existing vehicle search/tracking views. Toggle any module from **Settings** (admin) at runtime.

## Quick start (Docker)

```bash
docker compose up --build
# open http://localhost:8080  (admin / Admin@12345)
```

The compose file runs backend + worker in one container and nginx-served frontend in another. PostgreSQL is pre-wired but commented out — uncomment the `db` service and `DATABASE_URL` to switch from SQLite. Set `SECRET_KEY` and `POSTGRES_PASSWORD` via a `.env` file next to `docker-compose.yml`.

## Configuration

All configuration is environment-based (see `.env.example`). Highlights:

| Variable | Default | Purpose |
|---|---|---|
| `SECRET_KEY` | dev placeholder | JWT signing — **must** be changed for any real use |
| `DATABASE_URL` | SQLite | PostgreSQL recommended beyond local demos |
| `MAX_CONCURRENT_STREAMS` | 8 | per-worker source cap (deliberately small) |
| `DETECTION_SAMPLE_INTERVAL` | 1.0 s | AI pass frequency per camera |
| `OCR_MIN_CONFIDENCE` | 0.55 | below this, plate reads enter the review queue |
| `ENABLE_GPU` | false | use CUDA when the torch build supports it |
| `ENABLE_REID` / `ENABLE_ATTRIBUTES` / `ENABLE_PERSON_MODEL` / `ENABLE_QUALITY` / `ENABLE_ANOMALY` | true | independent switches for the five optional AI modules |
| `REID_SIMILARITY_THRESHOLD` | 0.72 | cosine similarity above which a Re-ID candidate match is recorded (always unconfirmed) |
| `ANOMALY_SPEED_LIMIT_KMPH` | 90 | estimated speed above which movement is flagged for human review |

Runtime-tunable subset (confidence thresholds, health interval, stream cap…) is editable from **Settings** in the UI (admin only) and persisted in the database.

## Security notes

- Passwords hashed with bcrypt; JWTs with expiry; role checks on every mutating endpoint.
- Camera credentials live in a dedicated table, are combined into RTSP URLs only inside the worker, and are never returned by the API (URLs are redacted `rtsp://***:***@host`).
- Audit trail for logins, camera/user changes, alert handling, settings and report exports.
- Stream endpoints accept `?access_token=` (browser `<img>` limitation) — kept to those endpoints only.
- Rate limiting on the API (streaming/media exempt), CORS allow-list, env-based secrets, no sensitive values in logs.
- For production: run behind HTTPS, set a strong `SECRET_KEY`, remove demo accounts, switch to PostgreSQL, and review `docs/SCALABILITY.md`.

## Known limitations (honest list)

- Single ingestion worker per process (horizontal scale-out design described in docs, not implemented).
- Cross-camera *identity* tracking requires readable plates; the optional Re-ID module provides appearance-based candidate matches but always labels them **unconfirmed**.
- MJPEG is bandwidth-hungry compared to HLS/WebRTC; fine for a PoC grid, documented as an upgrade path.
- OCR accuracy depends on camera angle/lighting; the review queue exists because reads *will* be wrong sometimes.
- No video-archive playback (detection images + metadata only) — retention/archival seam is described in the docs.
